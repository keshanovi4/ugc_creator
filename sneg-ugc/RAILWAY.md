# Технический пилот на Railway

Подготовлено 26 октября 2026 года. Railway пока не подключён: проект, диск и облачное развёртывание не созданы. Нужен новый пилотный Telegram-бот. Существующие бот и Google-форма не меняются.

## Назначение

Railway подходит для проверки приложения с вымышленными анкетами. Собственный домен не нужен: можно сгенерировать адрес `*.up.railway.app` с HTTPS. Caddy и `compose.yaml` здесь не запускаются.

В списке регионов Railway нет Казахстана. Перед переносом реальных анкет оператору нужно подтвердить размещение основной базы и копий: статья 12 закона РК о персональных данных предусматривает хранение в базе на территории РК. Применимость к оператору и трансграничную обработку следует проверить; согласие кандидата само по себе не заменяет требования хранения. Вариант сервера в Казахстане сохранён в `DEPLOY.md` и внешнем `UGC-pilot-launch.md`.

## Настройки сервиса

Создать отдельный проект `sneg-ugc-pilot`, один сервис приложения и один постоянный Volume. Источник — эта папка с Dockerfile. Если загружен весь внешний каталог, корень сервиса — `sneg-ugc`; если только содержимое этой папки — `/`.

| Настройка | Значение |
|---|---|
| Builder | Dockerfile |
| Dockerfile | `Dockerfile` в корне приложения |
| Start Command | оставить Docker CMD: `node server/index.mjs` |
| Healthcheck Path | `/healthz` |
| Replicas | `1` |
| Serverless / App Sleeping | выключено: планировщик работает в процессе |
| Volume Mount Path | `/app/data` |
| Public Networking | Generate Domain |

Для первого запуска достаточно панели. Устаревший `railway.json` для нового сервиса не создаётся: актуальная альтернатива — Infrastructure as Code. После подключения фактические настройки можно импортировать через `railway config pull`, не выгружая секреты в исходники.

Приложение читает платформенный `PORT`; значение по умолчанию — 3000. Docker healthcheck использует тот же порт. Публичный домен должен вести на этот порт.

### Права диска

Dockerfile запускает приложение как `node` (UID 1000). Railway предупреждает о возможных проблемах записи непривилегированного пользователя в Volume. Перед запуском проверить запись в `/app/data` от UID 1000. При `EACCES` инициализировать владельца этого каталога и каталога копий как `1000:1000` через административный доступ к контейнеру, затем снова запустить от `node`.

Официальный обход Railway — `RAILWAY_RUN_UID=0`, но он запускает весь процесс как root. Не включать его молча как постоянное значение. Права конкретного Volume ещё не проверены; этот этап выполняется после подключения аккаунта.

## Переменные

Вводить значения в Railway Variables. Токены не присылать в чат и не коммитить. Для теста с новым ботом и вымышленными анкетами использовать защищённый production-режим:

```dotenv
NODE_ENV=production
DEMO_MODE=false
HOST=0.0.0.0
DATABASE_PATH=/app/data/ugc.sqlite
BACKUP_DIRECTORY=/app/data/backups
BUSINESS_TIMEZONE=Asia/Almaty
AI_PROVIDER=rules
PUBLIC_URL=https://ЗАМЕНИТЬ-на-фактический-домен.up.railway.app
BOT_USERNAME=ЗАМЕНИТЬ-на-username-нового-бота-без-@
BOT_TOKEN=ЗАМЕНИТЬ-в-панели-Railway
ADMIN_IDS=ЗАМЕНИТЬ-на-числовой-Telegram-ID
SESSION_SECRET=ЗАМЕНИТЬ-на-отдельный-случайный-секрет-32-или-больше-символов
TELEGRAM_WEBHOOK_SECRET=ЗАМЕНИТЬ-на-другой-случайный-секрет-24-или-больше-символов
```

Это шаблон. После Generate Domain подставить настоящий HTTPS-адрес без завершающего `/`. Два разных секрета сгенерировать локально, выполнив дважды:

```sh
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

Production запрещает `DEMO_MODE=true`. Для просмотра без бота остаётся опубликованная закрытая демонстрация Sites. Не использовать открытый демо-API для реальных данных: деморежим не проверяет личность.

## Проверка запуска

1. Подключить Railway или подготовить проект в своём аккаунте. Проверить тариф и расходы: постоянное размещение не считать гарантированно бесплатным.
2. Создать сервис, подключить Volume, задать переменные, проверить права записи. Секреты сохранить только в Railway.
3. Сгенерировать домен, обновить `PUBLIC_URL`, применить настройки и развернуть. Проверить HTTPS и `/healthz`.
4. В контейнере сервиса выполнить `node scripts/setup-telegram.mjs`: скрипт меняет webhook и меню нового пилотного бота. Проверить webhook без вывода токена в журналы.
5. Открыть `/start`. Проверить роли с отдельными Telegram-аккаунтами: кандидат видит только свою заявку; менеджер принимает решение. Пройти путь от анкеты до выбора менеджера на вымышленных данных.
6. Повторить клик и решение второго менеджера, затем перезапустить и повторно развернуть сервис. Заявки и история должны сохраниться. Volume не удалять; у сервиса с диском возможен короткий перерыв при redeploy.
7. Создать копию командой ниже и проверить восстановление в отдельной базе. Назначить ежедневное резервирование и защищённую копию отдельно от этого Volume.
8. Проверить запланированное действие после периода без посещений: сервис не должен засыпать. `/healthz` проверяет HTTP, а не все внешние подключения.
9. Перед реальным набором подтвердить размещение данных, оператора, политику и бриф. После этого подключать настоящий поток и Threads.

```sh
node scripts/backup.mjs
```

`BACKUP_DIRECTORY=/app/data/backups` сохраняет копии на постоянном Volume при redeploy. Копия рядом с базой не защищает от потери самого Volume. Скрипт не запускает расписание и не удаляет старые копии; свободное место нужно контролировать.

Локально проверяются сохранение базы, копирование работающей WAL-базы, восстановление и целостность копии. Реальные Railway Volume, публичный домен, расходы и внешние сообщения ещё не проверены. Локальный тест не означает успешное облачное развёртывание.
