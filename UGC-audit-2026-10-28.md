## Баги и незавершённые сценарии

### AUD-01 · P1 · Форма теряет введённые данные

**Воспроизведено в браузере.** На втором шаге ввёл ссылку, отметил готовность снимать крупный план, нажал «Обновить». Ссылка исчезла, отметка сбросилась. Первый шаг также сохраняется только при переходе дальше, а не при вводе.

`show()` заменяет весь DOM, а `collectDraft()` вызывается только при переходе/отправке. Восстановление видимости документа вызывает тот же `refresh()`: это затрагивает сценарий возврата за ссылкой из другого приложения. Возврат из настоящего Instagram на телефоне отдельно не воспроизводился; путь обработчика подтверждён кодом.

**Исправление:** обновлять черновик на input/change; хранить его отдельно для пользователя и кампании; не заменять заполненную форму фоновым обновлением статуса. При изменении аккаунта удалять доступ к чужому черновику. Согласия повторно запрашивать при изменении условий.

### AUD-02 · P1 · Обновление очереди скрывает загруженные страницы

**Воспроизведено в браузере на 84 новых анкетах.** Сначала 40 строк, после «Показать ещё» — 80. После «Обновить» осталось 40 строк второй страницы; первая заявка изменилась с SN-0017 на SN-0061. Первые 40 записей остались в базе, но исчезли из отображаемой очереди.

`offset` остаётся 40, а `refresh(false)` заменяет список ответом только для этого offset. После следующей загрузки можно дойти до конца списка, так и не вернув первый блок. При ошибке загрузки offset тоже увеличивается заранее и не откатывается.

**Исправление:** хранить число загруженных строк и обновлять весь видимый диапазон либо явно возвращать очередь к началу. Сдвигать offset только после успешного ответа; объединять строки по ID. Сохранить позицию и фильтры при возврате из карточки.

### AUD-03 · P1 · Недоступный менеджер блокирует расписание Threads

**Воспроизведено скриптом.** Добавлены два менеджера; Telegram для второго возвращает `TELEGRAM_BLOCKED`. Два последовательных tick завершаются ошибкой, запросов к Threads — 0, просроченный scheduled-пост остаётся в расписании.

Ошибка отправки отдельного уведомления уже перехватывается. Но ошибки обновления карточки и общей подборки выходят из `interactiveTick()` раньше публикаций. Состояние `shortlist_dirty` не сбрасывается, поэтому ситуация повторяется. Это возможно также с ID менеджера, который ещё не начал диалог с ботом. Обработка части входящих заданий до этого места продолжает работать — речь не об остановке всего HTTP-сервера.

**Исправление:** изолировать ошибки каждого получателя, добавить backoff и статус недоступного менеджера. Отделить расписание Threads от рассылки менеджерам; показать владельцу конкретную ошибку.

### AUD-04 · P1 · Открытая веб-карточка остаётся устаревшей

Обновление очереди читает overview/list/campaign/posts/connections, но не перечитывает `state.detail`. Карточка продолжает показывать старые данные. ### AUD-13 · P2 · Ограничитель запросов считает IP прокси

**Локально воспроизведено, масштаб на Railway требует проверки сетевых логов.** 200 разных forwarded-адресов за одним TCP-peer делят один счётчик; запрос 601 блокируется. Код использует только `req.socket.remoteAddress`. На Railway это создаёт риск общего лимита для множества пользователей за edge-прокси. Блокировка реальных кандидатов на Railway в этом аудите не вызывалась.

**Исправление:** после входа лимитировать по проверенному Telegram ID; до входа — по адресу клиента из корректно настроенной доверенной границы прокси. Не доверять произвольному клиентскому X-Forwarded-For. Railway документирует X-Real-IP для адреса клиента: [официальные сетевые параметры](https://docs.railway.com/networking/public-networking/specs-and-limits#technical-specifications).

## Эксплуатация и накопление данных

- **Автокопии:** в приложении есть ручной согласованный backup, но нет расписания. Включено ли платформенное расписание Railway сейчас, этим аудитом не проверялось. Нужны ежедневная копия, отдельное хранение и проверенное восстановление. Снимок рядом с базой не покрывает потерю всего Volume.
- **Наблюдаемость:** `/healthz` проверяет ответ HTTP. `telegram=true` означает наличие токена, `aiConnected` — наличие настройки, а не успешную доставку/оценку последней заявки. Ошибки jobs доступны API владельца, но не выведены в полноценный экран. Нужны возраст старейшего задания, последняя успешная доставка, failed-задания и безопасный retry.
- **Рост базы:** `store.all()` загружает весь JSON всех анкет для фильтрации, счётчиков и нескольких фоновых проходов. При 400 заявках ежедневно за 180 дней появится около 72 тысяч анкет. Это расчёт размера потока, не результат нагрузочного испытания. Перенести фильтры/сортировку/пагинацию и агрегаты в SQL; измерить задержки на накопленной базе.
- **Хранение:** `retentionDays=180` объявлен в кампании, но удаления/анонимизации по сроку нет. Updates, idempotency и завершённые jobs тоже не очищаются. Нужны утверждённые сроки и отдельная безопасная задача очистки; действующие заявки удалять автоматически без согласованной политики нельзя.
- **Релизы:** пока использовать одну реплику SQLite и постоянный Volume. Проверять восстановление после SIGTERM, незавершённую публикацию, повтор webhook и сохранность подключений. Эти основы уже частично покрыты существующими тестами.

## Порядок работы

1. **Надёжность:** AUD-01…05, AUD-14; затем цикл ИИ и выдача данных кандидату. Добавить регрессионные проверки до выкладки. Критерий: форма/очередь не теряют состояние, недоступный менеджер не мешает публикациям, старые версии требуют осознанного повторного подтверждения.
2. **Рабочий интерфейс:** компактная очередь, работа в первом экране карточки, восстановление после конфликта, видимые ошибки интеграций, единое время и ручная сверка поста. Критерий: последовательный разбор с телефона и возврат из внешнего портфолио не сбивают контекст.
3. **Несколько сотрудников и эксплуатация:** разделение прав, управление командой, назначение кандидатов, резервирование, очистка и SQL-пагинация. Критерий: сотрудник добавляется без редактирования окружения; проблемы доставки видны владельцу; восстановление проверено на отдельной базе.

Браузерные регрессии нужны отдельно от нынешних модульных тестов: переключение аккаунтов, возврат из другого приложения, 80+ загруженных строк, обновление открытой карточки, потеря ответа при сохранении поста. Нынешняя frontend-проверка входа проверяет шаблоны исходника; она не заменяет исполнение этих сценариев в браузере.
